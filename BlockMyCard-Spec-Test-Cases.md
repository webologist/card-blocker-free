# BlockMyCard — Requirements Test Cases

**Source requirement doc:** "Overall flow" (Google Doc, `11GDGEF3ASwQNC55A-3rNc8o4e1EJ-afzKobxL5VNTyk`)
**Application:** BlockMyCard.in (card-blocker)
**Prepared:** 13 August 2026
**Purpose:** Every test case below traces to one line of the spec document, not to a screen or a role. Where the earlier execution audit (`QA-TEST-CASES.md`) already found a defect that a case would hit, it's cross-referenced by `BUG-ID` so the two documents don't duplicate discovery work. Where a spec item has no code behind it yet, the case is marked accordingly from static inspection of `app.js`, `index.html`, `server.js` and the `admin-*.js` bridges — mark it "confirm on next execution pass" rather than trusting the note blindly, since inspection can miss runtime-only behaviour.

## Legend

**Priority:** P0 = blocks the core "block a stolen card" journey · P1 = spec-required, not on the critical path · P2 = polish / nice-to-have per spec
**Status column values:** `Implemented` (code found, behaviour not verified live) · `Not implemented` (no matching code found) · `Partially implemented` (some code path exists but doesn't fully satisfy the requirement) · `Known defect: BUG-xx` (already logged in QA-TEST-CASES.md)

## 2. Registration

> *"Any user can register via mobile number by authenticating his OTP."*

**Clarified by product (13 Aug 2026): registration and login are the same OTP flow — there is no separate "Log in" entry point.** A user enters a number and verifies OTP; if the number is new, an account is created; if the number already exists, the same action logs them into their existing account automatically. The UI should never ask the user to choose between "Register" and "Log in," and correct OTP on an existing number must never overwrite or reset that account. **The already-registered case, and everything else about returning to the app after initial setup, is consolidated in Section 4 (Re-login) rather than here.**

## 3. Post-registration — card setup

> *"Once registered user would be prompted to select Type of card / Select bank / Add last 4 digits... option to save for future use... prompted to add email and alternative number... alternative number authenticated... YES → charge Rs.50/card, NO → free-tier message."*

**Clarified by product (13 Aug 2026): the Yes/No "save for future use" decision comes right after card details are entered, and email + alternate-number collection (CARD-06/07/08) only happens if the user says Yes (CARD-09).** Saying No must skip straight to the free-tier message — the app must not ask for email or an alternate number at all on the free path.

**⚠ Execution finding (13 Aug 2026, localhost:3000), resolved 14 Aug 2026 (NEW-02).** Choosing YES charges the ₹50/card and shows "Payment successful (simulated). Cards saved ✓" **immediately** — email/alternate-number collection then appears afterward as **Step 3 of 3 "Emergency contact details."** This step was originally skippable via a "Skip for now" link, so CARD-06/07/08 were reachable-but-optional after payment rather than a required step the Yes path had to pass through. Product decided (14 Aug 2026) this should be mandatory, not skip-then-remind: the "Skip for now" link has been removed from `app.js`, and the "Save & continue" action now requires both a non-empty, validly-formatted email and a non-empty alternate number before it will proceed — it then always routes into the alternate-number OTP-verification screen (CARD-07), and only reaches the dashboard once that OTP is verified. There is no longer a path from payment to the dashboard that bypasses this step.

## 9. Cross-cutting — traceability gaps worth flagging back to product

These aren't test cases so much as places where the spec and the shipped app have already diverged, surfaced while mapping requirements to code:

1. **Persistence (ADM-09 / RELOGIN-01, 02, 14) — fixed and re-verified 14 Aug 2026, no longer the top blocker.** The app now persists to Supabase server-side (via `server.js`/`pages/api/storage.ts`), not `localStorage` only, and the phone-token auth path (BUG-01) is confirmed working live. A second, more severe bug (NEW-08) was found and fixed in the course of verifying this: even with server persistence working, the client only fetched `cbp:users`/`cbp:logs`/`cbp:feedback` once at page mount before login, so a returning user on a fresh tab would have their real account silently overwritten with a blank one on ordinary login. Both are now fixed and live-verified (see RELOGIN-02, ADM-09, ADM-10). Remaining open items worth product attention: RELOGIN-14 (concurrent multi-device sessions) still needs an explicit product decision and a live two-device test now that the underlying data layer is fixed; log writes (see former NEW-06) are now deduped server-side, but the design of always re-sending a caller's whole known history on every write is still more chatty than necessary and worth revisiting if `cbp:logs` grows large again.
2. **Payment gateway (PAY-02 / ADM-13).** Spec lists four gateway options as if interchangeable. Only Razorpay has a working checkout path; the other three collect credentials but don't charge anyone. Admin UI should not let those three look production-ready until they're wired up.
3. **Admin authorisation (ADM-02).** Spec specifies one admin number but doesn't specify *how* that's enforced. Today it's a client-side string comparison with no server check, which combined with open dummy-OTP (BUG-03) means the admin console is effectively public. Highest-priority gap to close before any real user data touches the system.
